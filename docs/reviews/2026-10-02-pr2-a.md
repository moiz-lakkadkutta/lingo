## Things that check out

### Authn and authz
- `allowCode` is passed only on `GET /me`, `GET /me/words`, `POST /me/reviews` and `GET /me/stats` (`routes/me.ts:21,26,54,77,103`).
- Every other route calls `learner(req)`, so it ignores `x-session-code`: `PUT /me`, `POST /me/words`, `/me/progress`, `/me/level`, `/me/library`, `/catalog`, `/clips/:slug` and `/iap/*`.
- Writes are scoped by owner:
  - `POST /me/reviews` loads the word with `findFirst({ id, learnerId })` and answers 404 for another learner's word.
  - Progress, level and the save are keyed on `l.id`.
- `/iap/verify` refuses a request with no `x-device-id` (400).
- `LearnerDto.parse` strips `deviceId` and `id` on `GET /me` and `PUT /me`.

### Session codes and the rate limit
- A malformed code and an unknown code both answer 404 `UNKNOWN_CODE` and count a miss per IP.
- The HTTP path (`lib/learner.ts`) and the socket `join` (`sockets.ts:28-38`) share one limiter. They use the same IP format, because Express `req.ip` and `handshake.address` are both the raw socket address.
- `newCode` has no modulo bias, since 256 % 32 = 0.

### Log redaction
- pino-http redacts both credential headers (`app.ts:21,31`).
- Socket.IO traffic never goes through pino-http.
- The RVS client logs only `e.name` and the status, never the URL or the secret.
- `index.ts:8` logs the mode and `RVS_ENV`, never the secret.

### Entitlement and RVS
- **Review-007 H1 is fixed correctly.**
  - `refreshStale` re-verifies every not-cancelled row older than 24 h, at most 5 per call and at most once an hour per row. It runs on `GET /me` (`learnerOut(…, true)`) and on `GET /iap/status`.
  - `isActive` and `activeWhere` agree.
  - A row lapses at `renewalDate + 3 d`.
  - The save gate and `/iap/verify` never wait on RVS.
- **Review-007 M5 is fixed.** `savesSince` uses `startOfUtcDay`.

### Reviews and SM-2
- Reviews are idempotent:
  - A `reviewId` already recorded returns the current schedule.
  - The `updateMany` is conditional on the schedule it read.
  - A P2002 is caught.
  - `@@unique([savedWordId, reviewId])` allows many NULLs on Postgres, so reviews without an id are fine.
- SM-2 is unchanged from base and matches its comment: Anki-style ease, first steps of 1 and 6 days, and Hard ≥ interval + 1.

### Level rule
- Only attempts with ≥ 5 items, on a clip at or above the learner's level, count.
- Consecutive attempts on the same clip collapse to the latest.
- The two newest attempts must be on distinct clips and both ≥ 90 %.
- The level never moves down, and B2 stays B2.
- `total` comes from the server's count of quiz items (409 on a mismatch), and `correct ≤ total` is enforced in `LevelPut`.

### Zod validation
- Every body is validated: `LearnerSettingsPatch` (`.strict()`), `SaveWord`, `ReviewPost`, `ProgressPut`, `LevelPut`, `VerifyReceipt` (length-capped) and the `/catalog` query.
- Socket payloads go through `safeParse`.

## Medium

### M1. The production guard for Lingo Plus only runs when `NODE_ENV=production`, and nothing sets that, so review-007 M2's scenario still gives Plus away

**Where.**
- `apps/api/src/lib/env.ts:23`: `if (raw.NODE_ENV !== 'production' || …) return []`
- `apps/api/package.json`: `"start": "node dist/index.js"`, which does not set `NODE_ENV`.
- `turbo.json:3-23`: `globalEnv` does not list `NODE_ENV`.
- `.env.example`: has no `LINGO_PLUS_MODE`, `RVS_ENV`, `RVS_SHARED_SECRET` or `NODE_ENV`.
- `apps/api/src/routes/iap.ts:44`: test receipts are refused only when `RVS_ENV === 'production'`.

**Defect.** The fix for review-007 M2 is incomplete. Decision 0012 says "A production deploy cannot hand out Plus by accident". In fact the guard is opt-in:
- Without `NODE_ENV=production`, `plusSafetyProblems` returns `[]`. The API then starts in mode `iap` against the RVS Cloud Sandbox and accepts `testTransaction: true` receipts.
- With `LINGO_PLUS_MODE=demo` it starts silently.
- Nothing in the repo sets `NODE_ENV`: not the start script, not `.env.example`, not infra (there is no API stack).
- Turbo 2 runs in strict env mode, and `NODE_ENV` is not in `globalEnv`. So an operator who exports `NODE_ENV=production` and starts through turbo (`pnpm dev`, which is `turbo run dev`) still has the variable stripped before the API sees it.

**Reproduction.**

```
$ env -i PATH=… DATABASE_URL=… node --import tsx -e "const m=await import('./src/lib/env.ts'); …"
{"mode":"iap","rvs":"sandbox","allowed":[],
 "wouldBeProd":["RVS_ENV=sandbox (default) verifies against the RVS Cloud Sandbox, which accepts test receipts",
                "RVS_SHARED_SECRET is the default; production RVS needs the Developer Console shared key"]}
$ env -i … LINGO_PLUS_MODE=demo node … → "demo boots, problems allowed= []"
```

A scratch turbo workspace with `globalEnv: ["RVS_ENV"]`, run as `NODE_ENV=production PORT=5555 RVS_ENV=production LINGO_PLUS_MODE=demo turbo run show`, printed:

`NODE_ENV=undefined PORT=undefined RVS_ENV=production LINGO_PLUS_MODE=undefined`

**Failure scenario.** This is review-007 M2's scenario, unchanged.
1. The demo API is deployed with only `DATABASE_URL`, by `pnpm --filter @lingo/api start` or by `pnpm dev`.
2. Anyone sideloads App Tester and "buys" `lingo.plus.monthly`.
3. Sandbox RVS answers 200 with `testTransaction: true`.
4. `/iap/verify` answers `active, fulfil: true`, and Plus is granted with no warning in the log.

**Fix.** Make the guard fail closed instead of depending on an ambient variable. Any one of these works:
- Run `plusSafetyProblems` whenever `LINGO_PLUS_MODE !== 'off'`, unless `LINGO_DEV=true` or `RVS_ENV=sandbox` is set explicitly. "Explicitly" means `raw.RVS_ENV` is present, not defaulted.
- Or set `NODE_ENV=production` in the `start` script (`NODE_ENV=production node dist/index.js`), and add `NODE_ENV` (and `PORT`, see L5) to `turbo.json` `globalEnv`.

In both cases:
- Add `LINGO_PLUS_MODE`, `RVS_ENV`, `RVS_SHARED_SECRET` and `NODE_ENV` to `.env.example`, with comments.
- Add a test asserting that `assertPlusSafe` throws for `{}` raw env plus `LINGO_PLUS_MODE=demo` when the chosen trigger is set.

## Low

**L1. `POST /me/words` with an unknown `highlightId` answers 500.**
- Where: `apps/api/src/routes/me.ts:36`, with `SaveWord` in `packages/contracts/src/index.ts:43` (`highlightId: z.string()`).
- Defect: the upsert's `create` hits the foreign key (Prisma P2003). The error falls through to `errorHandler`, which returns `500 INTERNAL` and writes the stack with `console.error`.
- Probe Q1: `500 {"success":false,"error":{"code":"INTERNAL",…}}`.
- Scenario: a stale client, or a clip re-imported with new highlight ids, gets a 500 instead of 404. Each one also logs a stack trace.
- The same handler accepts a highlight from an unpublished clip; the probe fixtures use `status: 'ready'` and the save succeeds.
- Fix: look up the highlight with its clip's status first (`findFirst({ id, cue: { clip: { status: 'published' } } })`) and `throw notFound('Highlight')`. Alternatively, map P2003 to 404 in `errorHandler`.

**L2. `x-device-id` is never validated, so a long value answers 500.**
- Where: `apps/api/src/lib/learner.ts:36` and `apps/api/src/routes/sessions.ts:22`.
- Defect: any header string is upserted into `Learner.deviceId @unique`. Probe Q2 sent a 5.3 KB value and got Postgres `54000 index row size 5352 exceeds btree version 4 maximum 2704 for index "Learner_deviceId_key"`, so the response was 500.
- Every GET on `/catalog`, `/clips/:slug` and `/me` also creates a learner row for any new id. An unauthenticated client can grow the `Learner` table without bound.
- Fix: add a `DeviceId` schema in contracts that matches decision 0014's per-install id (for example `^[A-Za-z0-9_-]{8,128}$`). Validate it in `learner()` and in `POST /sessions`, and answer 400 `VALIDATION`.

**L3. A missing `x-device-id` falls back to the shared `'anon'` learner on every route except `/iap/verify`.**
- Where: `apps/api/src/lib/learner.ts:36` and `apps/api/src/routes/sessions.ts:22`.
- Defect: review-007 L3 was fixed only for `/iap/verify`. These routes still act on one learner shared by every header-less client:
  - `PUT /me` (settings)
  - `POST /me/words`, which counts against a shared limit of 20 a day
  - `PUT /me/level`, `PUT /me/progress`
  - `GET /iap/status`
  - `POST /sessions`, which hands out the anon learner's session code
- Scenario:
  1. A client that has not loaded its device id yet calls `PUT /me {native:'tr'}`, or calls `POST /sessions`.
  2. Every other such client now reads `native: 'tr'`, or gets the same code.
  3. A phone that pairs with that code reads and grades the shared words.
- Fix: refuse a request without `x-device-id` with 400 in `learner()` when `allowCode` resolves no code, and in `POST /sessions`. Keep a default only where a test needs it.

**L4. The free-tier limit can be overrun by concurrent saves.**
- Where: `apps/api/src/routes/me.ts:33-36`.
- Defect: the `savesSince` check and the upsert are not atomic.
- Probe Q3: 19 saves, then 10 concurrent saves. Two of the 10 got `limit:false`, ending at **21** saved for the day (limit flags `true,true,true,false,true,true,false,true,true,true`).
- Impact is small (+1 to +N for a client that fires in parallel).
- Fix: count and insert in a serialisable transaction, or take `pg_advisory_xact_lock(hashtext(learnerId))` around the check and the insert.

**L5. Turbo strict env mode strips `PORT` (and `NODE_ENV`) for tasks.**
- Where: `turbo.json:3-23`.
- Defect: `PORT` is read by `env.ts` but is missing from `globalEnv`. `pnpm dev` (`turbo run dev`) therefore always listens on 4000, whatever the shell exports. The scratch-turbo output under M1 shows `PORT=undefined`.
- The stale `RVS_SECRET` (`turbo.json:14`) is still present. It is tracked as review-007 L7 in TASKS.md:46 and is not counted here.
- Fix: add `PORT` and `NODE_ENV` to `globalEnv` and remove `RVS_SECRET`.

**L6. The production guard ignores `RVS_BASE`.**
- Where: `apps/api/src/lib/env.ts:22-29` and `apps/api/src/lib/rvs.ts:22-24`.
- Defect: `RVS_BASE` overrides the endpoint that `RVS_ENV` picks. `RVS_ENV=production` plus a leftover `RVS_BASE=https://appstore-sdk.amazon.com/sandbox`, or a local fake RVS URL, passes the guard. Test receipts are then refused only because `RVS_ENV` says production; a fake RVS can answer anything.
- Fix: in `plusSafetyProblems`, report any `raw.RVS_BASE` in production that is not `https://appstore-sdk.amazon.com`.
