## High

### H1 — `packages/pipeline/src/batch/run.ts:93` with `plan.ts:147-148`: a manifest-problem block is ignored when the clip's first step is skipped

- **Defect.** `planBatch` puts the per-clip `block` on `steps[0]` only, and that step can also carry `skip`. `runBatch` tests `step.skip`
  first and `continue`s, so it never reaches the `block` check. The other stages of the clip then run normally. The dry run tests `block`
  before `skip` (`command.ts:202`), so it prints `BLOCKED` while a real run goes ahead.
- **Scenario (reproduced).** This is row 6, `terra-x-so-trinken-baeume`. Runbook Phase 0 tells the human to set `verifiedOn` on the four
  manual rows. After that, the `verify` step is skipped ("manual check verified on …"). If the human has not yet found the full ZDF credit
  (the register cuts it at "Jochen …"), the clip still runs every stage. Probe output for a manual-verified clip whose attribution contains
  `…`: `status: "ok"`, exec calls `curl → ffprobe → ffmpeg → ffprobe → aws s3 cp → ffmpeg poster`, and `prepare` called. In `--phase final`
  it publishes a CC BY clip with a cut-off attribution, which breaks the plan's rule "validation must fail until fixed" (§2.3 row 6). The
  same hole lets other per-clip problems through, for example a native without an HLS name. That clip pays for Transcribe and Translate and
  then fails at packaging.
- **Fix.** In `runBatch`, test `step.block` before `step.skip`, or have `planBatch` put the block on a step that is never skipped (drop
  `skip` when adding `block`). Add a run test: a manual-verified clip with a placeholder attribution makes no exec, no prepare call, and
  reports `status: failed`.

### H2 — `plan.ts:123` and `:136`, `estimate.ts:215`; root cause `prepare.ts:77-84`: Transcribe runs again when `transcript.json` exists but `mezz.mp4` does not, and the dry run says it will not

- **Defect.** The batch passes `--reuse` only when both `transcript.json` and `mezz.mp4` exist (`plan.ts:123`). The spend flag
  (`transcribe = !cues && !exists(transcript.json)`, `plan.ts:136`) and the estimate (`estimate.ts:215`) look at `transcript.json` alone.
  `prepare` without `reuse` always calls `deps.transcribe` and then overwrites `transcript.json` (`prepare.ts:77-84`).
- **Scenario (reproduced).** With only `work/clip-1/transcript.json` present, the probe gave `reuse: undefined, transcribe: false`, and the
  estimate charged 0 min. A real run then starts a new Transcribe job and replaces the stored transcript. This happens whenever the large
  mezzanine has been deleted to save disk, or when only `transcript.json` was carried over from the Gate A work directory. Row 3's planned
  `--reuse` depends on exactly that directory. The cost is small (about $0.09–0.18 per clip). The real damage is that two guarantees the
  docs make are false: "Transcribe never runs twice" and docs/aws.md:13 "transcript.json is reused (--reuse, batch never deletes it)". The
  "Transcribe will run for" line, which exists to make spend visible before a run, under-reports.
- **Fix.** Pass `reuse: true` whenever `transcript.json` exists and `cues` is not set. `prepare` already handles a missing mezzanine: it
  re-downloads and normalises, and still reuses the transcript (`prepare.ts:64-65, 77`). Then the flag, the estimate and the argv agree. Add
  a plan test for "transcript without mezz → --reuse, no Transcribe".

## Medium

### M1 — `plan.ts:106, 110-111, 118, 131-135`: resume is keyed on file existence, not on the inputs, so segment edits are ignored

- **Defect.** Each stage decides whether to skip by whether a file exists:
  - `fetch`: the source file exists (any size).
  - `cut`: `_cuts/<slug>.mp4` exists.
  - `upload`: `_cuts/<slug>.uploaded` exists.
  - `prepare`: the marker key, which includes source/lang/natives/formality/cues/vttNote but not `segment`.

  None of these looks at `segment.in` or `segment.out`.
- **Scenario.** After `--phase draft`, the human reviews the cues and moves the out-point. Following the runbook they delete the cut and
  re-run. `cut` makes a new file. `upload` is skipped because `.uploaded` exists, so S3 keeps the old cut. `prepare` is skipped because the
  marker matches. The report says `ok`. In `--phase final`, `--reuse` packages the old mezzanine. The old segment is published with nothing
  telling the human. A second case: a Ctrl-C during the 800 MB row-1 download leaves a partial `_sources` file. The next run skips `fetch`
  and its duration probe, `cut` then fails the length check on every run, and deleting the cut does not clear it.
- **Fix.** Write a small JSON marker next to the cut holding `{in, out, downloadUrl}` and skip `cut` only when it matches. Put the same key
  in the upload marker and in the prepare `markerKey`. When the segment changes, invalidate `mezz.mp4` and `transcript.json`, or refuse the
  run and say what to delete. Download to `<file>.part` and rename it only after ffprobe passes.

### M5 — `plan.ts:85, 126-128`; `cli.ts` `--force-ai`: the Gate C escape hatch also publishes to the live CDN

- **Defect.** The guard itself is sound. `planBatch` throws for `phase final && gateC !== 'passed' && !forceAi`. It is reached from the
  dry run and from `runBatch`, and no stage subset or `--only` bypasses it. But `--force-ai` is documented as being "for a deliberate test
  run", and it switches on the whole final phase: `publish: true`, `ai: true`, and the poster `publish-extra`.
- **Scenario.** The human tests prompt changes with `--phase final --force-ai --only terra-x-friedlaender`. Unreviewed Nova glosses and quiz
  items are pushed to `published/<slug>/` behind CloudFront, which the app reads. That is the outcome the guard exists to prevent.
  `spot-check` already covers testing glosses without publishing.
- **Fix.** Make `--force-ai` imply no publishing (`publish: false`, no `publish-extra`) unless an explicit `--publish` flag is also given, or
  point the guard message at `pnpm pipeline spot-check` instead. Add a test that `forceAi` plans no `publish-extra` and `input.publish ===
  false`.

  `^[a-z0-9-]+$`, and output paths are `join(work, slug)`. Fix: restrict to `^https://` and require `cues` to resolve inside the manifest
  directory.
