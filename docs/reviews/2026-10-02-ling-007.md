## Things that check out

- **Merge `ff61469`, `apps/api/src/routes/me.ts:16`.** `GET /me` is `const l = await learner(req); ok(res, { ...l, plus: await entitled(l.id) })`, which is correct. `POST /me/words` (`me.ts:23-28`) also uses `learner(req)` plus `entitled(l.id)` and `FREE_SAVES_PER_DAY`. The LING-006 imports were kept.
- **Verify, then fulfil.** `packages/shared-ui/src/plus/flow.ts:13-24` calls `store.fulfil` only after `/iap/verify` answers `fulfil: true`. When verify throws, the receipt is not fulfilled (`purchaseFlow` catches the throw and returns `verifyError`). The server never sets `fulfil: true` for non-`iap` modes, for RVS errors, for a wrong SKU or for a production test receipt.
- **RVS client, `apps/api/src/lib/rvs.ts`.**
  - All three path segments go through `encodeURIComponent` (the one gap is L1).
  - Status mapping: 400 is `invalid_receipt`, 496 is `invalid_secret`, 497 is `invalid_user`, and any other status is `rvs_error`.
  - A thrown fetch or the 5 s abort is `network`. The abort timer also covers `res.json()`, so a slow body is caught.
  - The client never throws. It logs only `e.name`, never the URL or the secret, and there is a test for that.
  - The route checks `receipt.receiptId !== body.receiptId`, so RVS cannot answer for a different receipt.
- **shared-ui stays Vega-safe.** `src/plus/*`, `src/platform/*` and `screens/Plus.tsx` import only react, react-native, `@lingo/contracts` and `@moizp/vega-media-kit`. Neither `react-native-iap` nor `@amazon-devices/*` appears, and the eslint deny-list passes. The plugin test lives in `shared-ui/test/`, outside the linted `src/`.
- **The PEM never reaches git.** `apps/expo/.gitignore` ignores `amazon/AppstoreAuthenticationKey.pem`, and the root `.gitignore` ignores `apps/expo/android`, so the copy in `android/app/src/main/assets` is ignored too. The plugin's `setStoreProperty` is idempotent and replaces `fireOsEnabled`.
- **Deep-link parsing.** `parseLaunchUri` anchors the scheme and host and applies `^[a-z0-9-]{1,80}$` to the raw (undecoded) slug, so `%2e`, `/` and uppercase are rejected. `useLaunchIntents` opens only slugs that are in the loaded catalog.
- **Plus screen copy and focus.** Every button goes through `Focusable`, which provides the aria-label, the outline and the 1.04 scale. There are at most three focusables, and Subscribe is absent when there is no price. Busy states use a polite live region, and there is no countdown or strike-through. Copy passes `lint:words`.

## High

### H1. Plus never ends on the server unless the client opens the Plus screen, and only the newest purchase is ever re-checked
**Where.**
- `apps/api/src/lib/entitlement.ts:27-34` (`entitled`)
- `entitlement.ts:59-67` (`plusStatus` re-verify)
- `apps/api/src/routes/me.ts:16` and `me.ts:25` (the gates)

**Defect.**
- `entitled()` only checks the stored `cancelDate` and never re-checks with RVS. The only re-verify path is `GET /iap/status`, which the client calls only when the Plus screen mounts.
- Even that path re-verifies only the purchase with the latest `purchaseDate`. Any older row with `cancelDate: null` keeps granting Plus forever.
- Decision 0009 §5 relies on the client for all three ways a cancellation reaches the server: re-verify, restore and lazy status. Today none of the three runs. The Plus screen and the startup restore are not wired into Root (see M1). A tampered or old client can also simply never call `/iap/status`.

**Scenario (probe P1).**
1. A learner verifies a monthly receipt, then cancels it in Amazon.
2. Thirty days later RVS reports a `cancelDate`.
3. `GET /me` still returns `plus: true`, with no RVS call made. Output: `P1 /me plus = true rvs calls = 0`.
4. The 20-a-day limit and Challenge mode stay unlocked indefinitely.

**Scenario (probe P2).**
1. A learner has an older receipt with `cancelDate: null` that is stale (verified 30 days ago), and a newer cancelled receipt.
2. `GET /iap/status` re-verifies only the newer one. Output: `re-verified = ['p2new-…']`.
3. RVS would now cancel the older one, but it is never asked, and the response says `plus = true`.

**Fix.**
- Move the stale check into one helper, `refreshStale(learnerId, rvs, now)`. It re-verifies **every** row that has `cancelDate` null or in the future and `verifiedAt` older than 24 h, or a bounded number of rows per call.
- Call it from `GET /me`, which runs on every app start, as well as from `/iap/status`. Then `entitled()` reads fresh rows.
- Alternatively, compute expiry on the server: store `renewalDate` and treat a row as active only while `renewalDate + grace > now`, re-verifying when it lapses. That bounds Plus to one billing period even if RVS is never called.
- Add a test: `GET /me` with a row verified 25 h ago, where RVS now returns a `cancelDate`, must give `plus: false`.

### M2. Plus can be had for free if the API is deployed with the default settings (sandbox RVS, sandbox secret, demo mode unguarded)
**Where.**
- `apps/api/src/lib/env.ts:10-13`: `LINGO_PLUS_MODE` defaults to `iap`, `RVS_ENV` to `sandbox` and `RVS_SHARED_SECRET` to `'sandbox'`.
- `apps/api/src/routes/iap.ts:44`: test receipts are rejected only when `RVS_ENV === 'production'`.

**Defect.** Nothing in `infra/` deploys the API with these variables, and every default fails open:
- A production API started without `RVS_ENV=production` verifies against the RVS Cloud Sandbox and accepts `testTransaction: true` receipts. The sandbox accepts any secret. App Tester receipts come from any Fire TV with ADB sandbox mode on, and those are exactly the steps in our own README.
- `LINGO_PLUS_MODE=demo` left over from filming gives everyone Plus. Nothing logs it and nothing refuses it.
- `RVS_ENV=production` with the defaulted secret `'sandbox'` silently answers 496 for every purchase. Those receipts are reported as `unavailable` and never fulfilled.

**Scenario.**
1. The API is deployed for the video and judges with only `DATABASE_URL` set.
2. Anyone runs `adb shell setprop debug.amazon.sandboxmode debug`, installs App Tester and "buys" `lingo.plus.monthly`.
3. `/iap/verify` returns `active, fulfil: true` and Plus is granted.

**Fix.**
- When `NODE_ENV === 'production'`, refuse to boot unless `RVS_ENV` is set explicitly, and when `RVS_ENV=production`, unless `RVS_SHARED_SECRET` is set to something other than `'sandbox'` (a Zod `superRefine` in `env.ts`).
- Log `{ LINGO_PLUS_MODE, RVS_ENV }` once at startup, without the secret.
- Reject `testTransaction` unless `RVS_ENV === 'sandbox'` (an allow-list instead of a deny-list).
- Remove the stale `RVS_SECRET` entry in `turbo.json:14` (see L7).

### M3. After a successful charge, the Plus screen says "Nothing was charged"
**Where.**
- `packages/shared-ui/src/plus/machine.ts:49-50`: `verified` with `plus: false`, and `verifyError`, both go to `back('retry')`.
- `packages/shared-ui/src/strings.ts:28`: `retry` reads "That didn't go through. Nothing was charged that we can see. Try again or restore."

**Defect.** When the store has already reported `purchased`, Amazon has charged the learner. If verify then returns `unavailable` (RVS 5xx, network or 496), returns `invalid`, or throws, the learner sees a sentence saying nothing was charged. That is false, and it invites a second purchase attempt. The second attempt gets `alreadyOwned` and goes to restore, which hits the same RVS outage and ends on "No Lingo Plus purchase found".

**Scenario (probe P5).** offer → subscribe → `purchased` → `verified { plus:false, outcome:'unavailable' }` gives `{"phase":"offer","price":"2,99 €","note":"retry"}`, which renders the retry line above.

**Fix.**
- Add a note `'pending'` for the `verifying` → failure path, for example "Amazon took the payment. We're still confirming it. Select Restore in a minute." Keep `retry` for store-side errors before any receipt exists.
- Add an `it()` that checks a verify failure after `purchased` never shows `retry`.

### M4. Restore says "No Lingo Plus purchase found" when the store simply failed, and it hides the price for a learner who has Plus
**Where.**
- `packages/shared-ui/src/plus/flow.ts:44-45`: an error from `store.restore()` is swallowed and becomes `[]`.
- `machine.ts:37`: `active` + `restore` gives `busy` with `price: null`.
- `machine.ts:51`: an empty restore gives `offer` with `note: 'restoreEmpty'`.

**Defect.**
- A store failure is a normal sandbox event: App Tester is flaky, `getPurchaseUpdates` answers FAILED and is mapped to `[]`, or `initConnection` rejects. The learner is told no purchase exists for their account.
- When Restore starts from `active`, the screen drops to `offer` with `price: null`. It shows "Price unavailable right now." and hides Subscribe, but the server still says `plus: true`. Probe P4 output: `{"phase":"offer","price":null,"note":"restoreEmpty"}`.

**Scenario.** A subscribed learner presses Restore while App Tester is not answering. The screen reads "No Lingo Plus purchase found for this Amazon account. Price unavailable right now." The learner still has Plus everywhere else in the app.

**Fix.**
- Let `restoreFlow` emit a distinct `restoreError` when `store.restore()` throws or the store answers a non-SUCCESSFUL code, and map that to the M3 `pending`/`retry` wording.
- Restore started from `active` should return to `active` unless the server reports `plus: false`, for example by re-fetching `/iap/status`.
- Keep the last known price in the `busy` state that starts from `active`.

### M5. The free-tier day boundary depends on the host's time zone and disagrees with the UTC days used elsewhere
**Where.**
- `apps/api/src/routes/me.ts:26`: `today.setHours(0,0,0,0)`.
- `apps/api/src/lib/entitlement.ts:51`: `savesSince` uses the same rule.
- Compare `apps/api/src/lib/day.ts:1`: "Every 'day' in LING-006 is a UTC calendar day".

**Defect.** "Local midnight" means the API process's time zone, not the learner's. After the merge, the streak, `due=today` and stats use UTC days, while the save limit uses the server's local day. So the limit's day moves with the deployment's `TZ`.

**Scenario.** At 2026-10-01 22:30Z:
- On a laptop with `TZ=Europe/Berlin` (filming), the limit window starts at `2026-10-01T22:00Z`, so the count resets.
- On a UTC host, the window starts at `2026-10-01T00:00Z`, and `utcDay` is still `2026-10-01`.

The same learner gets a fresh 20 saves 30 minutes after hitting the limit on one host, and not on the other. The phone's "today" deck and the TV's "That's 20 today" also disagree. The commands I ran were `TZ=UTC` versus `TZ=Europe/Berlin` with `node -e` against `setHours`.

**Fix.** Use one helper, `startOfUtcDay(now)` from `lib/day.ts`, in both `me.ts:26` and `savesSince`, so all "today" rules match decision R5. A per-learner time zone stays the LING-006 follow-up. Add a test that pins the boundary with an injected `now`.

## Low

**L1. `.` and `..` survive `encodeURIComponent` in RVS path segments.** `apps/api/src/lib/rvs.ts:55`, with the input limits in `packages/contracts/src/iap.ts` (`receiptId`/`userId` min 1).
- `encodeURIComponent('..') === '..'`, and WHATWG URL parsing in `fetch` collapses dot segments.
- Probe P3: `verify('..', '..')` requests `/sandbox/version/1.0/verifyReceiptId/developer/s/`.
- Impact is limited: the host stays the same, and `receiptId` equality is checked afterwards. Still, a client can steer the server's outbound request to other Amazon paths that carry the secret.
- Fix: reject `.` and `..`, or restrict both fields to `^[A-Za-z0-9._:=+/-]+$`-style values that are not dot-only, in `VerifyReceipt`. Alternatively, encode `.` as `%2E` in `enc`.

**L2. The Vega Content Launcher answers SUCCESS for unknown slugs.** `apps/vega/App.template.tsx:17` passes `() => null` as `knownSlugs`. So any well-formed `lingo_slug` returns `SUCCESS`, and the app then ignores it in Root. This contradicts plan §G4, README step 6 ("unknown slug answers URL_NOT_AVAILABLE") and checklist B7. Fix: have Root publish the catalog slugs into a module-level set that the handler reads, or document the deviation in the checklist.

**L3. `/iap` uses its own `learner()` helper.** `apps/api/src/routes/iap.ts:16`.
- After the merge, `/me` uses `lib/learner.learner(req)`, which honours `x-session-code`. `/iap/*` keys on `x-device-id` only and falls back to the shared `'anon'` learner.
- A request with no `x-device-id` that verifies a receipt gives Plus to every other header-less client.
- Fix: use `learner(req)` from `lib/learner`, and refuse `/iap/verify` without an `x-device-id`.

**L4. Anyone holding another learner's receiptId and Amazon userId can take over their receipt.** `iap.ts:50-55`: the upsert `update` moves `learnerId`.
- This was accepted in decision 0009, and RVS still requires the matching userId. Both values are stored in our DB and on the device, though, and learner identity is an unauthenticated `x-device-id`.
- Record the residual risk in 0009.
- Consider refusing a takeover while the current owner's row is active and was verified in the last 24 h, or at least logging takeovers.

**L5. `plusStatus` can report a past end date while `plus` is true.** `entitlement.ts:70`. `cancelsAt` and `renewsAt` come from the newest row, but `plus` is computed from any row. Probe P2 returned `plus: true` with `cancelsAt` in the past, so the active screen reads "You have Lingo Plus. Ends 1 October." about a date that has gone by. Fix: take the dates from the row that grants the entitlement.

**L6. A re-verify whose receiptId does not match does nothing, silently, on every call.** `entitlement.ts:62-66`.
- When RVS returns a different `receiptId`, the code does not log and does not update `verifiedAt`, so every `/iap/status` call hits RVS again (up to 5 s each).
- The re-verify path also skips `acceptsSku` and the production `testTransaction` check that `/verify` applies.
- Fix: log it, bump `verifiedAt` (or mark the row), and reuse the `/verify` acceptance checks.

**L7. `turbo.json:14` still lists `RVS_SECRET`.** The variable was renamed to `RVS_SHARED_SECRET`. An operator who sets the old name gets the default `'sandbox'` without any warning. Remove it, or fail at boot when `RVS_SECRET` is set (see M2).

**L8. The deep-link `t` has no upper bound.** `packages/shared-ui/src/platform/launch.ts:41`. `lingo://clip/x?t=999999999` passes `positionS` straight through. Clamp it to `[0, durationS]` in `onOpen`, or cap it in the parser.

**L9. `PUT /me` returns the stored `plus` column.** `me.ts:18`. The handler returns `db.learner.update(...)`, which is the cached `plus`, while `GET /me` returns the computed value. Root ignores the PUT body today, but the phone or a later caller could act on a stale `true`. Return `{ ...row, plus: await entitled(row.id) }`, or omit `plus`.

**L10. EAS builds ship without the PEM.** `apps/expo/package.json` runs `build:tv` as `eas build`. EAS uploads the project according to `.gitignore`, so the git-ignored `amazon/AppstoreAuthenticationKey.pem` never reaches the build. The plugin warns, and the APK has no key (`AUTH_TOKEN_VERIFICATION_FAILURE`). Document an EAS file secret, or `.easignore` plus a `prebuild` step, in `apps/expo/README.md`.

**L11 (nit). `LaunchBridge.tsx` location.** It sits at `apps/expo/LaunchBridge.tsx` instead of the plan's `apps/expo/src/LaunchBridge.tsx`. That is harmless, and tsconfig includes it.
